# RuralBrain 微服务架构设计

## 概述

RuralBrain 采用微服务架构，将系统拆分为多个独立部署、独立扩展的服务单元。

---

## 服务拆分原则

### 1. 按业务能力拆分

每个服务专注一个具体的业务能力：

| 服务 | 能力 | 端口 |
|------|------|------|
| **检测服务网关** | 图像检测（病虫害、大米、奶牛） | 8001 |
| **规划咨询服务** | 乡村规划知识库咨询 | 8003 |
| **后端主服务** | Agent 编排、智能路由、流式响应 | 8081 |
| **前端应用** | 用户界面、交互展示 | 3001 |

### 2. 独立数据存储

- **检测服务**：模型文件独立存储（`src/algorithms/detection/models/`）
- **规划服务**：ChromaDB 独立存储（`knowledge_base/chroma_db/`）
- **前端应用**：无状态，数据来自后端 API

### 3. 独立部署和扩展

每个服务可以：
- 独立启动和停止
- 独立配置资源限制
- 独立进行版本升级
- 按需扩展实例数量

## 服务间通信

### 同步通信（HTTP REST API）

**当前实现**：所有服务间通信使用 HTTP REST API

**优点**：
- 简单直观，易于调试
- 支持流式响应（SSE）
- 与 FastAPI 自然集成

**缺点**：
- 同步调用，可能阻塞
- 网络故障会影响可用性

### 异步通信（未来规划）

**考虑场景**：
- 批量检测任务
- 知识库构建
- 长时间分析任务

**技术选择**：
- Redis Streams
- RabbitMQ
- 或直接使用 Celery

## 服务治理

### 服务发现

**当前方案**：硬编码服务地址（`localhost:端口`）

**改进方向**：
- 开发环境：保持 localhost
- 生产环境：使用环境变量或服务注册中心

### 负载均衡

**当前方案**：单实例部署

**改进方向**：
- 使用 Nginx 反向代理
- Docker Compose 多实例部署
- Kubernetes（如需要）

### 熔断降级

**当前方案**：Agent 层面处理服务不可用

**改进方向**：
- 添加熔断器（Circuit Breaker）
- 服务降级策略（检测服务不可用时返回友好提示）

## 检测服务网关化

### 背景问题

原始设计中，每个检测类型是一个独立服务：
- 病虫害检测：`localhost:8000`
- 大米品种识别：`localhost:8001`
- 奶牛检测：`localhost:8002`

**问题**：
- 端口管理复杂（3 个独立端口）
- 客户端需要知道每个服务的地址
- 服务间调用分散

### 网关化方案

将所有检测服务整合到统一网关：
- 统一入口：`localhost:8001`
- 路由区分：
  - `/detection/pest/*` → 病虫害检测
  - `/detection/rice/*` → 大米品种识别
  - `/detection/cow/*` → 奶牛检测

**效果**：
- 端口从 3 个减少到 1 个
- 客户端只需知道网关地址
- 统一的接口规范

详见：[检测服务网关化决策](../decisions/detection-gateway.md)

## 规划服务独立部署

### 为什么独立部署？

**业务原因**：
- RAG 知识库是一个独立的能力领域
- 规划咨询的调用模式与检测不同
- 知识库更新和维护频率独立

**技术原因**：
- ChromaDB 需要独立的资源
- RAG 检索可能需要更多 CPU/内存
- 知识库构建是长时间任务

### 独立部署架构

```
规划服务 (8003)
    │
    ├─ FastAPI 服务入口
    ├─ Planning Agent (LangGraph)
    ├─ RAG 核心工具 (7 个)
    └─ ChromaDB 向量数据库
```

## 后端主服务职责

### 定位

后端主服务是系统的**统一编排中心**，不是业务服务。

### 核心职责

1. **API 网关**：统一入口、CORS 处理
2. **意图识别**：判断用户需要检测还是规划咨询
3. **Agent 编排**：通过 Orchestrator Agent V2 协调各服务
4. **流式响应**：SSE 实时返回结果

### 不负责

- 具体的检测算法（由检测服务负责）
- 知识库检索（由规划服务负责）

## 部署模式

### 开发模式（Docker Compose）

```yaml
# docker-compose.dev.yml
services:
  backend:    # 后端主服务 :8081
  detection:  # 检测服务网关 :8001
  planning:   # 规划咨询服务 :8003
  frontend:   # 前端应用 :3001
```

**特点**：
- 支持热重载
- 卷挂载源码目录
- 详细日志输出

### 生产模式（Docker Compose）

```yaml
# docker-compose.yml
services:
  backend:    # 多进程部署
  detection:  # 资源限制优化
  planning:   # 资源限制优化
  frontend:   # 生产构建
```

**特点**：
- 生产镜像优化
- 资源限制配置
- 无热重载

## 服务依赖关系

### 核心服务（必需）

| 服务 | 依赖 | 被依赖 |
|------|------|--------|
| 前端应用 | 后端主服务 | - |
| 后端主服务 | 检测服务（可选）、规划服务（可选） | 前端应用 |

### 可选服务

| 服务 | 作用 | 不可用时的行为 |
|------|------|----------------|
| 检测服务网关 | 图像检测 | Agent 基于知识库回答 |
| 规划咨询服务 | 规划咨询 | Agent 告知用户服务不可用 |

### 最小启动

仅启动后端主服务和前端应用：
- 支持纯对话功能
- 检测和规划服务按需启动

## 监控和可观测性

### 健康检查

每个服务提供 `/health` 端点：

```bash
curl http://localhost:8081/health    # 后端
curl http://localhost:8001/health    # 检测网关
curl http://localhost:8003/health    # 规划服务
```

### 日志管理

**开发环境**：控制台输出
**生产环境**：建议使用集中式日志收集（ELK/Loki）

### 性能追踪

**可选**：集成 LangSmith 进行 Agent 行为追踪

## 扩展性考虑

### 水平扩展

- 前端：无状态，可直接扩展
- 后端：通过 Docker Compose `scale` 或 Kubernetes
- 检测服务：独立扩展（GPU 节点）
- 规划服务：独立扩展（大内存节点）

### 垂直扩展

- 检测服务：GPU 加速
- 规划服务：更多内存（ChromaDB）
- 后端服务：更多 CPU（Agent 计算）
