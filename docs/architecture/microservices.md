# RuralBrain 微服务架构设计

## 概述

RuralBrain 采用微服务架构，将系统拆分为多个独立部署、独立扩展的服务单元。

---

## 服务拆分原则

### 1. 按业务能力拆分

每个服务专注一个具体的业务能力：

| 服务 | 能力 | 端口 |
|------|------|------|
| **检测服务网关** | 图像检测（病虫害、大米、奶牛） | 8001 |
| **后端主服务** | Agent 编排、智能路由、流式响应（包含 RAG 知识库） | 8081 |
| **前端应用** | 用户界面、交互展示 | 3001 |

### 2. 独立数据存储

- **检测服务**：模型文件独立存储（`src/algorithms/detection/models/`）
- **RAG 知识库**：ChromaDB 存储在主服务（`knowledge_base/chroma_db/`）
- **前端应用**：无状态，数据来自后端 API

### 3. 独立部署和扩展

每个服务可以：
- 独立启动和（停）
- 独立配置资源限制
- 独立进行版本升级
- 按需扩展实例数量

## 服务拓扑

```
                     ┌─────────────────┐
                     │   前端应用      │
                     │   Next.js       │
                     │     :3001       │
                     └────────┬────────┘
                              │
                              ▼
                     ┌─────────────────┐
                     │  后端主服务     │
                     │  FastAPI + Agent│
                     │     :8081       │
                     └────────┬────────┘
                              │
            ┌─────────────────┼─────────────────┐
            │ 检测服务网关   │ RAG 知识库 │ 内置能力    │
            │    :8001      │ (Agent内部)   │  (Agent)    │
            ├─────────────────┼─────────────────┼────────────┤
            │ • 病虫害检测  │ • RAG 检索   │ • 定价分析    │
            │ • 大米品种    │ • 章节摘要   │ • 营销策略    │
            │ • 奶牛检测    │ • ChromaDB    │ • 农场检查    │
            └─────────────────┴─────────────────┴────────────┘
```

**说明**：
- RAG 知识库功能已集成到后端主服务中
- 规划技能（`src/rag/service/`）作为 Skill 集成到 Agent 内部
- 由 Agent 根据用户意图自动决定是否调用规划技能
- 规划技能内部根据前端知识库开关决定是否使用 RAG 工具

## 服务间通信

### 同步通信（HTTP REST API）

**当前实现**：所有服务间通信使用 HTTP REST API

**优点**：
- 简单直观，易于调试
- 支持流式响应（SSE）
- 与 FastAPI 自然集成

**缺点**：
- 同步调用，可能阻塞
- 网络故障会影响可用性

### 异步通信（未来规划）

**考虑场景**：
- 批量检测任务
- 知识库构建
- 长时间分析任务

**技术选择**：
- Redis Redis Streams
- RabbitMQ
- 或直接使用 Celery

## 服务治理

### 服务发现

**当前方案**：通过环境变量配置服务地址，默认值为 `http://localhost:端口`；在 Docker Compose 中由环境变量注入容器内服务名 URL

**改进方向**：
- 开发环境：继续使用 localhost 作为环境变量默认值，便于本地调试
- 生产环境：通过环境变量统一管理服务地址，必要时接入服务注册中心（如 Consul、Eureka 等）

### 负载均衡

**当前方案**：单实例部署

**改进方向**：
- 使用 Nginx 反向代理
- Docker Compose 多实例部署
- Kubernetes（如需要）

### 熔断降级

**当前方案**：Agent 层面处理服务不可用

**改进方向**：
- 添加熔断器（Circuit Breaker）
- 服务降级策略（检测服务不可用时返回友好提示）

## 检测服务网关化

### 背景问题

原始设计中，每个检测类型是一个独立服务：
- 病虫害检测：`localhost:8000`
- 大米品种识别：`localhost:8001`
- 奶牛检测：`localhost:8002`

**问题**：
- 端口管理复杂（3 个独立端口）
- 客户端需要知道每个服务的地址
- 服务间调用分散

### 网关化方案

将所有检测服务整合到统一网关：
- 统一入口：`localhost:8001`
- 路由区分：
  - `/detection/pest/*` → 病虫害检测
  - `/detection/rice/*` → 大米品种识别
  - `/detection/cow/*` → 奶牛检测

**效果**：

| 指标 | 改进 |
|------|------|
| 检测服务端口 | 3 → 1 (-67%) |
| 端口冲突风险 | 降低（避开 8080） |
| 文档更新点 | 多处 → 统一在 commands.md |

### 定性改进

1. **统一规范**
   - 端口分配有明确原则
   - 新服务端口选择有据可依

2. **降低维护成本**
   - 端口信息只在 `commands.md` 维护
   - 减少文档不一致问题

3. **改善开发体验**
   - 端口更易记忆（8081、8001、3001）
   - 避免常用端口冲突

## 配置位置

### 环境变量

```bash
# .env
PORT=8081                          # 后端主服务
HOST=127.0.0.1                     # 监听地址
ALLOWED_ORIGINS=http://localhost:3001  # CORS 配置
```

### 各服务配置

**后端主服务** (`service/settings.py`)：
```python
PORT = 8081
```

**检测服务网关** (`src/algorithms/api/main.py`)：
```python
PORT = 8001
```

**前端应用** (`frontend/package.json`)：
```json
{
  "scripts": {
    "dev": "next dev -p 3001"
  }
}
```

## 权衡和代价

### 优点

1. 端口分配有明确原则
2. 避免常用端口冲突
3. 降低维护成本
4. 改善开发体验

### 缺点

1. **迁移成本**：需要更新配置和文档
   - 缓解：一次性完成，后续稳定

2. **记忆更新**：开发者需要记住新端口
   - 缓解：更易记忆（8081 vs 8080）
