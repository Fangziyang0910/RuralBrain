# RuralBrain 系统架构设计

## 设计理念

RuralBrain 采用**微服务架构** + **Agent 编排** + **智能路由**的设计模式，为乡村治理和发展提供智能化决策支持。

### 核心设计原则

1. **微服务拆分**：各能力模块独立部署、独立扩展
2. **智能路由**：自动识别用户意图，分发到合适的服务
3. **Agent 编排**：通过 Orchestrator Agent 统一协调各服务能力
4. **渐进式披露**：按需加载能力，优化 Token 消耗

## 技术选型

### 后端框架：FastAPI

**选择原因**：
- 原生支持异步，高并发性能优秀
- 自动生成 OpenAPI 文档，降低维护成本
- 类型提示友好，与 Python 生态无缝集成
- 内置数据验证（Pydantic）

### Agent 框架：LangChain/LangGraph

**选择原因**：
- **LangChain**：提供丰富的 LLM 集成和工具抽象
- **LangGraph**：支持复杂的多步推理和状态管理
- **LangSmith**：提供可观测性和调试能力
- 生态活跃，社区支持良好

### 向量数据库：ChromaDB

**选择原因**：
- 轻量级，易于部署和维护
- 原生支持 embedding 相似度检索
- 与 LangChain 集成良好
- 无需额外基础设施

### 检测框架：ONNX Runtime

**选择原因**：
- 跨平台兼容性好
- 推理性能优异
- 镜像体积小（相比 PyTorch 减少 60-75%）
- 支持硬件加速（CPU/GPU）

### 层级职责

#### 1. 表现层（Frontend）
- **职责**：用户交互、数据展示
- **技术**：Next.js 14 + TypeScript + Tailwind CSS
- **特点**：单页应用、流式响应、多模态输入

#### 2. 网关层（Backend）
- **职责**：统一入口、意图识别、智能路由
- **技术**：FastAPI + Orchestrator Agent V2
- **特点**：SSE 流式响应、自动意图判断

#### 3. 能力层（Services）
- **检测网关**：统一检测服务入口（病虫害、大米、奶牛）
- **RAG 知识库**：向量数据库，已集成到 Agent 内部
- **内置能力**：定价分析、营销策略（Agent 内置）

## 关键设计决策

### 1. 微服务拆分原则

**问题**：为什么采用微服务架构？

**决策**：
- 各能力模块独立演进（检测算法更新不影响其他服务）
- 按需扩展（检测服务可能需要更多资源）
- 技术栈灵活（检测用 ONNX，RAG 用 LangChain）

**权衡**：
- 增加了部署复杂度 → 通过 Docker Compose 简化
- 服务间通信开销 → 通过统一网关优化

### 2. 检测服务网关化

**问题**：为什么将检测服务整合到统一网关？

**决策**：
- 简化端口管理（从 3 个端口减少到 1 个）
- 统一接口规范（所有检测服务使用相同的 API 格式）
- 简化客户端调用（单一入口）

详见：[检测服务网关化决策](detection-gateway.md)

### 3. Agent V2 Skills 架构

**问题**：为什么采用 Progressive Disclosure 设计？

**决策**：
- Token 消耗减少 50%+（按需加载技能）
- 提示词更简洁（从 82 行减少到 20 行）
- 模块化技能配置，易于扩展

**技术实现**：
- 技能抽象层（`src/agents/skills/base.py`）
- 技能注册中心（`src/agents/skills/registry.py`）
- 三个检测技能（病虫害、大米、奶牛）
- 新旧 Agent 共存，平滑迁移

**文档**：[V2 Agent 架构详解](architecture/v2-agent-architecture.md)

### 4. 智能路由设计

**问题**：如何自动判断用户意图？

**决策**：
- **规则 + LLM 混合**：简单场景用规则，复杂场景用 LLM
- **上下文感知**：结合对话历史和图片信息
- **优先级明确**：有图片 → 检测；规划关键词 → RAG；默认 → 对话

## 服务间通信

### 同步通信（HTTP REST API）

**当前实现**：所有服务间通信使用 HTTP REST API

**优点**：
- 简单直观，易于调试
- 支持流式响应（SSE）
- 与 FastAPI 自然集成

**缺点**：
- 同步调用，可能阻塞
- 网络故障会影响可用性

### 异步通信（未来规划）

**考虑场景**：
- 批量检测任务
- 知识库构建
- 长时间分析任务

**技术选择**：
- Redis Streams
- RabbitMQ
- 或直接使用 Celery

## 服务拓扑说明

当前系统只有以下容器：

1. **frontend** (3001) - 前端应用
2. **backend** (8081) - 后端主服务（包含 Agent V2 和 RAG 知识库）
3. **detection-service** (8001) - 检测服务网关

**说明**：
- RAG 知识库功能已集成到 backend 服务中
- 规划技能（`src/rag/service/`）作为 Skill 集成到 Agent 内部
- 由 Agent 根据用户意图自动决定是否调用规划技能
- 规划技能内部根据前端知识库开关决定是否使用 RAG 工具
