# RuralBrain 系统架构设计

## 设计理念

RuralBrain 采用**微服务架构** + **Agent 编排** + **智能路由**的设计模式，为乡村治理和发展提供智能化决策支持。

### 核心设计原则

1. **微服务拆分**：各能力模块独立部署、独立扩展
2. **智能路由**：自动识别用户意图，分发到合适的服务
3. **Agent 编排**：通过 Orchestrator Agent 统一协调各服务能力
4. **渐进式披露**：按需加载能力，优化 Token 消耗

## 技术选型

### 后端框架：FastAPI

**选择原因**：
- 原生支持异步，高并发性能优秀
- 自动生成 OpenAPI 文档，降低维护成本
- 类型提示友好，与 Python 生态无缝集成
- 内置数据验证（Pydantic）

### Agent 框架：LangChain/LangGraph

**选择原因**：
- **LangChain**：提供丰富的 LLM 集成和工具抽象
- **LangGraph**：支持复杂的多步推理和状态管理
- **LangSmith**：提供可观测性和调试能力
- 生态活跃，社区支持良好

### 向量数据库：ChromaDB

**选择原因**：
- 轻量级，易于部署和维护
- 原生支持 embedding 相似度检索
- 与 LangChain 集成良好
- 无需额外基础设施

### 检测框架：ONNX Runtime

**选择原因**：
- 跨平台兼容性好
- 推理性能优异
- 镜像体积小（相比 PyTorch 减少 60-75%）
- 支持硬件加速（CPU/GPU）

```
┌─────────────────────────────────────────────────────────────┐
│                      表现层 (Frontend)                        │
│                   Next.js + TypeScript                       │
│  - 聊天界面  - 图片上传  - 流式响应  - 结果可视化             │
└────────────────────────┬────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────────┐
│                      网关层 (Backend)                         │
│                   FastAPI + Orchestrator Agent               │
│  - 统一入口  - 意图识别  - 智能路由  - 流式响应               │
└──┬──────────────┬──────────────┬──────────────┬────────────┘
   │              │              │              │
   ▼              ▼              ▼              ▼
┌─────────┐  ┌─────────┐  ┌─────────┐  ┌──────────────┐
│检测网关 │  │规划服务 │  │内置能力 │  │ 外部服务     │
│  8001   │  │  8003   │  │ (Agent) │  │  (扩展)      │
└─────────┘  └─────────┘  └─────────┘  └──────────────┘
```

### 层级职责

#### 1. 表现层（Frontend）
- **职责**：用户交互、数据展示
- **技术**：Next.js 14 + TypeScript + Tailwind CSS
- **特点**：单页应用、流式响应、多模态输入

#### 2. 网关层（Backend）
- **职责**：统一入口、意图识别、智能路由
- **技术**：FastAPI + Orchestrator Agent V2
- **特点**：SSE 流式响应、自动意图判断

#### 3. 能力层（Services）
- **检测网关**：统一检测服务入口（病虫害、大米、奶牛）
- **规划服务**：RAG 知识库咨询
- **内置能力**：定价分析、营销策略（Agent 内置）

## 关键设计决策

### 1. 微服务拆分原则

**问题**：为什么采用微服务架构？

**决策**：
- 各能力模块独立演进（检测算法更新不影响其他服务）
- 按需扩展（检测服务可能需要更多资源）
- 技术栈灵活（检测用 ONNX，RAG 用 LangChain）

**权衡**：
- 增加了部署复杂度 → 通过 Docker Compose 简化
- 服务间通信开销 → 通过统一网关优化

### 2. 检测服务网关化

**问题**：为什么将检测服务整合到统一网关？

**决策**：
- 简化端口管理（从 3 个端口减少到 1 个）
- 统一接口规范（所有检测服务使用相同的 API 格式）
- 简化客户端调用（单一入口）

详见：[检测服务网关化决策](../decisions/detection-gateway.md)

### 3. Agent V2 Skills 架构

**问题**：为什么采用 Progressive Disclosure 设计？

**决策**：
- Token 消耗减少 50%+（按需加载技能）
- 提示词更简洁（从 82 行减少到 20 行）
- 模块化更易扩展（新增技能无需修改核心）

详见：[Agent V2 迁移决策](../decisions/agent-v2-migration.md)

### 4. 智能路由设计

**问题**：如何自动判断用户意图？

**决策**：
- **规则 + LLM 混合**：简单场景用规则，复杂场景用 LLM
- **上下文感知**：结合对话历史和图片信息
- **优先级明确**：有图片 → 检测；规划关键词 → RAG；默认 → 对话

## 服务间通信

### 同步通信（HTTP REST API）

**适用场景**：
- 实时检测请求
- 规划咨询查询
- 健康检查

**特点**：
- 简单直接
- 易于调试
- 支持流式响应（SSE）

### 异步通信（未来规划）

**适用场景**：
- 批量检测任务
- 知识库构建
- 长时间分析任务

**技术选择**：考虑使用消息队列（Redis Streams / RabbitMQ）

## 数据流设计

### 检测流程

```
用户上传图片
    ↓
前端发送请求（带图片路径）
    ↓
后端意图识别（有图片 → 检测）
    ↓
Agent 判断检测类型
    ↓
调用检测工具 → 检测网关 (8001)
    ↓
YOLO 模型推理
    ↓
返回检测结果 + Agent 生成建议
    ↓
SSE 流式返回前端
```

### 规划咨询流程

```
用户提出规划问题
    ↓
后端意图识别（规划关键词 → RAG）
    ↓
转发到规划服务 (8003)
    ↓
Planning Agent 使用 RAG 工具
    ↓
查询 ChromaDB 知识库
    ↓
返回基于知识库的建议
    ↓
SSE 流式返回前端
```

## 性能优化策略

### Agent 层面
- **Progressive Disclosure**：按需加载技能，减少 Token 消耗
- **工具选择优化**：根据上下文智能选择工具
- **缓存机制**：RAG 检索结果缓存

### 服务层面
- **异步处理**：FastAPI 异步路由
- **连接池**：HTTP 客户端连接复用
- **资源限制**：Docker 容器资源限制

### 部署层面
- **ONNX Runtime**：轻量级推理引擎
- **多进程部署**：生产环境多 worker
- **反向代理**：Nginx 负载均衡

## 扩展性设计

### 新增检测服务

1. 在 `src/algorithms/detection/` 添加新服务
2. 在检测网关注册路由
3. 在 Agent 添加对应工具
4. 更新技能定义

### 新增 RAG 工具

1. 在 `src/rag/core/tools.py` 定义新工具
2. 添加到规划服务工具列表
3. 更新文档

### 新增知识库文档

1. 将文档放入 `src/rag/docs/`
2. 运行 `uv run python scripts/dev/build_kb_auto.py`
3. 系统自动索引
